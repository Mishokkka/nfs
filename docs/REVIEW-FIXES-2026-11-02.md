# Исправления независимой проверки PR #5 — 2 ноября 2026

Исходная точка проверки — `8045b35`. Подтвердились два дефекта: автоматическое
восстановление копии sessionStorage захватывало живую гонку, а release job
переключал Latest до проверки запрета отката. Исправления остаются в том же PR.

## Восстановление и второе окно

`RaceRecoveryStore` по-прежнему хранит checkpoint в sessionStorage. Хранилище
может копироваться при открытии вкладки, поэтому оно больше не считается
доказательством отсутствия старого экземпляра ведущего.

Перед автоматическим захватом `RaceNetwork.restoreSavedRace()` выполняет
асинхронную проверку `RecoveryProbe`. Она использует прежние state-request и
сообщения владельца; протокол 19 и формат кадров не изменены. Ответ экземпляра
из сохранённой аренды сразу отменяет восстановление. Окно получает обычное
состояние гонки и остаётся клиентом. При молчании запрос повторяется раз в
секунду; проверка продолжается 3 с, охватывая штатный heartbeat 2 с.

Параллельные вызовы разделяют одну попытку. До захвата повторно проверяются
пользователь, аренда, поколение сетевой сессии, текущая гонка/лобби и tombstones.
Закрытие, shutdown, запуск тренировки, отключение сокета и приостановка вкладки
отменяют попытку. Поколение отмены защищает также промежуток между завершением
таймера и продолжением Promise. Кнопка открытия позволяет повторить проверку
после временного отключения; окно рисуется до ожидания.

Регрессия запускает реальные RaceNetwork, RaceSimulation и BigRacesApp с
моделью транспорта и Worker: сохранение tick 600 копируется в отдельное
хранилище, игрок уже получил tick 900. Немедленный/задержанный ответ и потеря
первого запроса сохраняют raceId, hostEpoch, tick 900 и единственный Worker.
Проверяются отмены, смена аренды/лобби, известный игроку финиш при старой аренде,
обычный F5, новый namespace управления
и восстановление ГМ без собственного болида.

Это ограниченный по времени детектор присутствия, а не распределённый lock.
Длительная потеря всех ответов при формально подключённом сокете всё ещё может
выглядеть как уход владельца. Epoch и новый transport raceId сохраняют прежнюю
защиту от поздних пакетов. Полный сетевой заезд в целевом Foundry остаётся
обязательным перед выпуском; проверки не доказывают отсутствие всех разрывов.

## Публичные каналы обновлений

Выпуски разных тегов проходят одну неотменяемую очередь `nfs-stable-release`.
Publisher читает опубликованный Latest и legacy main/module.json до публикации,
валидирует draft и assets и публикует с явным `make_latest: "false"`.
Затем повторяет проверки и продвигает сначала legacy через SHA, затем Latest.
Если хотя бы один канал уже новее, release остаётся только в истории.

Тесты `release-channel-tests.mjs` вызывают полный оркестратор с подставным API
и проверяют оба канала после каждого побочного эффекта. Покрыты порядок
0.18.0 → 0.17.1 и обратный, отсутствующий/отстающий legacy, первый выпуск,
отказ записи legacy, отказ финального переключения, повтор после частичного
успеха, неполные assets и внешнее продвижение во время публикации.

Между GitHub Contents API и Latest нет общей транзакции. При отказе последнего
шага legacy может временно опережать Latest, указывая на уже готовый выпуск.
Повтор publisher завершает продвижение. Произвольные ручные записи вне общей
очереди не получают атомарной защиты; границы описаны в RELEASING.md.

## Проверки и границы

`npm run test:all` прошёл: 8/8 быстрых групп, 9/9 интеграционных групп,
репрезентативные soaks (120 track / 30 wall / 50 pit seeds, городской заезд с
обязательным питом, выборка гонок и баланса элитных ботов). Число групп не равно
числу assertions; выборки не исчерпывающие. Сборка выпускает ZIP и manifest
из module-source.json; независимая сверка байтов всех entries фиксируется
в приложенных к работе локальных артефактах.
Никаких реальных выпусков, тегов, merge или записи публичного manifest при
локальных проверках не выполняется. Три согласованные рекомендации о новой
модели шин/yaw и prediction-контактах остаются следующим этапом.
